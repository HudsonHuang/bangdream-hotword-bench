# 从 live-interpreter + hotword-bench 沉淀的工程经验（完整版）

> 依据：上一个 session 的 36 个 turn（从装 exe、做 benchmark v0.1/v0.2、调热词、接 3.1，到 PR/打包）+ 本次的 3.1 调优、成本、gold-v0.3。
> 上一版总结只看了最后几次对话，漏了 benchmark 构建、虚警 frontier、规则门控被证伪、3.8-live 硬限制、接线 bug 这些关键段落。这里重写完整版。

## 两个仓库的背景

- **live-interpreter**：Windows 实时字幕/同传系统。启动器负责设置和音频设备，backend 负责起 worker；worker 从 stdin 读 16k PCM，把事件按 JSONL 打到 stdout。
- **bangdream-hotword-bench**：热词与流式评测集。v0.1 是 283 条句级切片，v0.2 是 dense-20 连续流，v0.3 是 32 条人工精标高光（92.4 分钟 / 1,525 cue）。
- 本文的结论来自 interp 仓库的 PR #2 调试过程，以及 benchmark v0.1→v0.3 的构建过程。

## 先纠正上一版漏掉的东西

1. **评测口径混用过。** 有一轮把「流式跑出来的 live 默认词表」放进了切片表；后来严格单句归属一改，qwen 流式 ASR F1 从 90.1 掉到 74.1。不是模型变了，是句子归属规则变了。
2. **规则门控被实测证伪。** 乐队名没有「ちゃん/さん」，旧规则会删掉真名字；在 ICL 输出上，规则门控删掉 14 个真名、只换掉 3 个假名，净亏。
3. **3.1 的 `input.context` 会让 ASR 召回掉约 3 个点。** 上下文应该给翻译，不要给识别。
4. **qwen3.8-live 有硬限制。** 会话约 15 分钟必断；`speaker_detection` VAD 对 3–10 秒短切片不触发，154/283 条空结果。这不是调参能救的，直接停测。
5. **热词接线出过静默 bug。** 启动器白名单漏了 `qwen3.1-audio`，GUI 里看着有热词，实际 worker 拿到的是 0 条，等于裸跑。
6. **超热词权重 50 会反噬长会话。** 短片段召回有效，但 37 分钟流式 ASR F1 从 90.1 掉到 85.7，误触发 3→15。
7. **上下文曾经把成本放大 7 倍。** `context_turns=0` 的 `[-0:]` 切片错误，把全部历史字幕塞进 prompt；3 分钟从 2.71 元/小时变成 19.9 元/小时。
8. **计时口径错过一次。** 回放时间戳从 worker 进程启动算，多算了 1–2 秒连接时间；首批「首字延迟」被高估，后来才用 `ready` 事件校正。
9. **数据完整性踩过坑。** HF 上的旧音频镜像解码只出 996 秒，FTP 原始数据才是对的；不校验就评测，结论会全错。

这些不是“细节”，它们直接改变了模型选型和最终默认配置。

## 1. 评测口径是第一个“模型参数”

**原则**：先定义“什么算对、时间从哪算、句子怎么归属”，再谈模型。

这个项目里：

- 切片口径和流式口径能差 10–20 个点；
- 同一段音频，严格单句归属和多归属能让 qwen ASR F1 差 16 个点；
- 首字延迟从「进程启动」还是「开始喂音频」算，能差 1–2 秒；
- 人工 SRT 和自动字幕的差别，足以让“调参收益”变成噪声；
- benchmark 本身要分层：v0.1 句级切片测名字召回、v0.2 连续流测真实断句、v0.3 手标高光测节奏/质量/热词。**不要用一套数据回答所有问题。**

**以后怎么做**：
- 每个指标写清楚：输入、输出、分母、时间零点、句子归属规则；
- 数据先做 checksum / 解码 / 时长校验；
- 同一张表绝不混口径；混过就标注并重算；
- 金标要有人工确认和歧义标注，v0.2 的 181 句里就有 9 行需要人工裁决。

---

## 2. 多目标 + 硬约束，而不是单一 F1

**原则**：质量、热词、延迟、成本必须同时可见；其中至少一个应该是硬约束。

这个项目的约束是“虚警不高于基线、最好减半”，不是“F1 最高”。于是才有后面的 frontier：

- 只换词表：召回 48→76%，虚警 8.5→14.8%，不达标；
- 换 reference 注入：虚警 25.4→17.6%，召回只掉 1.4pt，是唯一“两头都赚”的操作；
- ICL：虚警 13.4→6.3%，召回只掉 0.8pt，但输入 token +24.4%、单场 +0.31 元、p95 +141ms；
- 规则门控：虚警 4.9%，但真名被删 14 个，净亏，放弃；
- 3.1：召回更高、句子更整，但过插入更多、句子更长、单条等待更久。

**以后怎么做**：
- 先写“不可接受”的约束（虚警、成本、p95），再在可行域里挑质量；
- 不要用一个加权分把不同量纲的东西糊在一起；
- 约束变化时，重新跑 frontier，不要沿用旧结论。

---

## 3. 把系统拆成可独立复现的环节

**原则**：能离线复现的环节，不要每次端到端烧钱。

这个项目后来固定成三层：

- **ASR 层**：headless 喂 PCM，1x 实时，记录终句和时间轴；
- **MT 层**：固定同一份 ASR 文本，只重放 LLM 调用（705 次/配置，约 1.5 分钟），隔离翻译变量；
- **端到端**：1x 回放整段音频，记录每个事件的 `_recv_mono`，算首字/终态/空档。

**以后怎么做**：
- 每个环节都能单独 replay，输入固定、输出可 diff；
- 记录原始事件流，而不是只存汇总表；
- 端到端只做最终验证，不做日常调参。

---

## 4. 领域适配要匹配“上游表示”，并在部署分布上验证

**原则**：词表/术语只有匹配上游实际输出的形态才有用。

踩过的坑：

- 只给 17 条中文规范名，同传召回只有 22%，因为 ASR 输出的是假名，匹配不上；
- 词表必须带假名读音，召回才从 23–28% 到 76–83%；
- Paraformer 的语音偏置有效（召回 +28pt，误触发 0），qwen-audio 的内联词表几乎无效；
- 权重 50 在短片段有效，在 37 分钟长会话反噬；
- 3.1 的 ASR `context` 反而降召回；
- qwen3.8-live 效果不差，但 15 分钟断线 + 短切片 VAD 空结果，直接淘汰。

**以后怎么做**：
- 先过硬约束（会话时长、VAD 行为、成本、部署环境），再比效果；
- 先看上游模型实际输出的 token/文字形态，再设计词表和匹配；
- 同一个杠杆在“短样本/长会话”“离线/流式”“不同引擎”上分别验证；
- 部署分布（长会话、连续说话、噪声）才是最终裁判。

---

## 5. 精度杠杆有顺序：数据/表示 > 注入方式 > prompt 结构 > 规则后处理

**原则**：先修输入，再修说法，最后才考虑后处理规则。

这个项目的实际收益排序：

1. **词表/读音**：ASR 召回 45→77%，同传召回 28→76%；
2. **注入方式**：`force → reference` + 去 error-form 别名，虚警 25.4→17.6%，召回只掉 1.4pt；
3. **ICL 结构**：术语卡 + 4 条正负例，虚警 13.4→6.3%，召回 -0.8pt；
4. **规则门控**：虚警 4.9%，但真名被删 14 个，净亏；
5. **更多示例/同音词表/规则段/温度 0/4 句上下文**：基本不涨，甚至变差。

**以后怎么做**：
- 先问“输入表示对不对”，再问“prompt 怎么写”；
- 规则后处理只用于“低风险、可解释”的兜底，不要拿它当主精度杠杆；
- 领域专家的判断（乐队名没有敬称、同音词属性）比自动规则更可靠。

---

## 6. 上下文是成本/收益的联合优化

**原则**：上下文不是免费的；它的收益必须大于 token、延迟和错误传播的代价。

这个项目里：

- 当时默认带 2 句上下文，实测收益 <1 个点；关掉后指标几乎不变，成本更低；
- 3.1 的 ASR `input.context` 降召回，不要用；
- 本次 gold 集上，ICL + 1 轮上下文 charF1 0.456，reference 无上下文 0.445，但成本 3.68 vs 2.74 元/小时；
- 全量历史上下文（bug）让成本 19.9 元/小时，语义也没好到值得。

**以后怎么做**：
- 上下文按“轮数/字符/token”设上限；
- 默认关闭，用 A/B 证明收益后再开；
- 把上下文成本和延迟计入预算，而不是只算模型单价；
- 实验设预算和停止条件：有硬伤（15 分钟断线、短切片空结果）就停，不要为了“跑完整”继续烧钱。

---

## 7. 延迟和成本都要拆到链路；流式系统看首字

**原则**：端到端数字不能指导优化，必须拆成可操作的环节。

延迟链路：

```text
采集 → VAD 端点 → 网络 → LLM 首 token → 生成 → 渲染
```

这个项目的实际瓶颈：

- 3.1 慢不是推理慢，是**终句晚**：p50 1.56 秒；
- `max_sentence_silence=200` 在远场 VAD 下没用，换 `near_meeting_16k` 才把 p90 从 4.7 秒降到 2.7 秒；
- 流式翻译把首字从「终译后 1 秒」提前到「终译后 0.3–0.7 秒」；
- 4 秒草稿只对长句有效，短句不出草稿，避免无谓的质量风险。

成本链路：

```text
成本 ≈ 调用次数 × 每次 prompt token × 单价
```

- 3.1 在 200ms 断句下 3 分钟 72 次调用，调用频率比模型单价更关键；
- 修掉上下文 bug 后，成本 19.9→3.26 元/小时；
- reference 默认版 2.74 元/小时，与 Paraformer 基线 2.71 基本持平。

**以后怎么做**：
- 首字时间和终态时间分开测；
- 每次实验记录 token usage 和调用次数；
- 先优化调用次数和 prompt 大小，再考虑换模型。

---

## 8. 运行时、打包、接线都是模型系统的一部分

**原则**：模型效果只在“最终交付的运行时”里才算数。

这次踩的坑：

- Python 3.10 + OpenSSL 1.1 下，3.1 WebSocket 随机掉线；Python 3.13 + OpenSSL 3 稳定；
- Python 3.10 的 `urllib` 把 SSE 缓冲到连接结束，流式翻译变成 10 秒一次；改用 `http.client`；
- Python 3.13 移除 `audioop`，需要 `audioop-lts`；
- PyInstaller 的 hidden imports、backend 目录布局、zip 解压后的路径；
- 启动器白名单漏了 3.1，热词静默不生效；
- GUI 默认模型是 `qwen-mt-plus`，不支持 ICL，导致开关永远灰的。

**以后怎么做**：
- 在冻结产物上跑 smoke test 和最小端到端；
- 启动时打印“实际生效”的模型、VAD、词表数、prompt 模式；
- 给配置接线加集成测试，不要只测函数；
- 构建环境、Python/OpenSSL 版本写进 VERSION。

---

## 9. 失败模式和可观测性要提前设计

**原则**：云端/实时系统一定会掉线、卡住、超时；这些是正常路径。

这个项目做了：

- 掉线自动重连 + 退避；
- 翻译队列满时降级显示原文；
- 流式失败回退普通请求；
- 结构化 JSONL 日志：session config、hotword list、hotword hit、translation usage、reconnect；
- 用日志诊断“韩文/泰文”怀疑，结果是 0 条，真正问题是音乐/杂音段的非日文幻觉。

**以后怎么做**：
- 每个外部依赖都有超时、重试、降级；
- 日志记录“配置 + 输入 + 输出 + 耗时”，而不只是错误；
- 先看日志再改代码，不要用规则 guard 掩盖问题。

---

## 10. 交付和数据资产化是最后一道工程

**原则**：别人能按文档跑起来、能复现指标，才算交付。

这个项目最后沉淀了：

- HF 数据集：WAV/SRT + manifest + checksums + release tag；
- 评测脚本版本化：`eval_stream.py` 明确 coverage / first-zh / charF1 / 人名召回 / 成本；
- 复现入口：`tools/replay_stream.py` + `docs/BENCHMARK_V03.md`；
- 测试包：README-FIRST、VERSION、SHA256、不含任何人的 API Key；
- PR 描述用“小抄”这种可读的说法，附最少必要的指标。

**以后怎么做**：
- 数据、脚本、指标、构建物都版本化；
- 交付物带“怎么跑、怎么验、出问题看哪里”；
- 密钥、日志、个人配置不进入交付包。

## 附：在 live-interpreter 里怎么定位这些问题

这部分是“调试上下文”，也是上面很多结论的来源。

### 1. 先看“实际生效”的配置，不看 GUI 上写了什么

worker 启动时打三类日志：

```text
session: model=qwen-audio-3.1-asr-flash-streaming source=ja hints=['ja'] mt=reference
asr_config: max_end_silence=200 vad_model=near_meeting_16k vocabulary_terms=175
hotword_vocabulary: asr_terms=176 mt_terms=177
hotword_hit [123]: ゆのちゃん=>由乃酱
```

热词白名单漏掉 3.1 的那次，就是 `asr_config` 里 `vocabulary_terms=0` 才定位到的。  
**先证明配置到了 worker，再怀疑模型。**

### 2. 用 1x 回放代替真人直播，固定输入

```powershell
python tools/replay_stream.py --wav gold.wav --start 120 --seconds 180 --out runs/31_ref -- `
  --model qwen-audio-3.1-asr-flash-streaming --max-end-silence 200 `
  --vad-model near_meeting_16k --mt-model qwen3.8-max --mt-mode reference
```

- 音频按 100ms 一帧喂，和真实采集一致；
- 每个事件带 `_recv_mono`，才能算首字/终态/空档；
- 同一条 WAV 可以反复跑不同参数，排除“今天直播不一样”。

### 3. 把 ASR 和 MT 分开测

- 只跑 ASR：`--no-translation`，看终句长度、coverage、长句比例；
- 固定 ASR 文本，只重放 MT：`replay_mt` / `replay_stream`，隔离翻译变量；
- 端到端只做最后验收，不要拿它调 prompt。

### 4. 在冻结产物里再验一次

源码能跑、`python worker.py` 能跑，都不算数：

- 用 PyInstaller 打出 backend；
- 直接跑 `LiveInterpreterBackend.exe --qwen-asr-worker ...` 或解压 zip 后跑；
- 检查 backend 目录布局、`_internal` 里的 hotwords/name cards、Python/OpenSSL 版本。

### 5. 每次只改一个变量，保留 raw JSONL

- 固定 WAV、固定模型、固定 prompt，只改 VAD / 断句 / 注入方式；
- 原始 `events.jsonl` 保留，换评分脚本可以重算；
- 记录 token usage、调用次数、reconnect 次数；
- 主观体验（草稿闪不闪、空档明不明显）单独记，不混进客观表。

### 6. 交付前做一次“别人视角”的检查

- 解压 zip，从零启动；
- 确认 README 里的 API Key、引擎、音频设备步骤都对；
- 确认包里没有自己的 Key、日志、临时配置；
- 确认 `VERSION.txt` / commit / 构建时间和实际二进制一致。

## 一个可复用的实验闭环

```text
定义指标/约束
  → 固定数据与口径（checksum、时间零点、句子归属）
  → 跑基线
  → 单变量改动（数据/表示 → 注入 → prompt → 后处理）
  → 多片段 + 长会话验证
  → 成本/延迟预算
  → 用户短时体验
  → 冻结默认 + 打包 + 版本化
```

## 如果只记五条

1. **先定口径，再比模型。**
2. **多目标 + 硬约束，别追单一 F1。**
3. **拆环节复现，端到端只做最终验证。**
4. **词表/表示先对，再谈 prompt 和规则。**
5. **在最终运行时里验证，失败和交付都算工程。**
